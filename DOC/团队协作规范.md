# 团队协作规范（OWNER ↔ Team Lead ↔ Agent Team）

> **这份是什么**：OWNER 与 AI 团队的协作口径——谁跟谁讲话、流程怎么跑、闸门谁把关。
> **和别的文件的分工**：功能该长怎样→`BUSINESS_LOGIC_PRINCIPLES.md`｜怎么改代码→`DEVELOPMENT_GUIDE.md`｜跳转→`PAGE_MAP.md`｜栏位→`FIELD_DICT.md`｜现状与决策→`进度总览.md`。

---

## 1. 沟通方式

| 项目 | 规则 |
| --- | --- |
| OWNER 的对口 | **只有 Team Lead**，不直接对 agent |
| Agent 之间 | **不能互相对话**，一切经 Team Lead 转手 |
| 回报者 | Team Lead 彙整后回报，agent 原始报告不直接呈现 |
| 回报形式 | **对话内条列／表格**，不另开 MD 档 |
| 分歧处理 | 各 agent 意见不同时，**原样列出分歧点**，不只给 Team Lead 结论 |
| 打断 OWNER 的时机 | 只在规格有洞、决策冲突、产品取舍；纯技术问题 Team Lead 自决 |

## 1.1 Agent 交付方式（踩过的坑）

Agent 的最终回覆**不会自动送到 Team Lead**，必须主动呼叫 `SendMessage({ to: "main", ... })` 把报告全文送出。

| 规则 | 说明 |
| --- | --- |
| 报告全文进 `message` | 不是摘要、不是档案路径。Team Lead 只看得到送出的这段文字 |
| 只送 idle 通知不算交件 | 会被视为没做 |
| 派工时必须明写 | Team Lead 下指令时要讲清楚交付方式，**这是派工方的责任**，不是 agent 的疏失 |

**这条已写进全部 5 个 agent 定义档**（`.claude/agents/*.md` 末段）。

## 2. 团队成员

| 角色 | 职责 | 定义档 |
| --- | --- | --- |
| PM | 规格：需求／画面／导航／系统逻辑／完整性自稽 | `.claude/agents/PM.md` |
| RD1 | 实作（与 RD2 平行，自行协调边界） | `.claude/agents/RD1.md` |
| RD2 | 实作（与 RD1 平行，自行协调边界） | `.claude/agents/RD2.md` |
| 稽核RD | 稽核：逻辑／规格符合度／整合冲突／安全 | `.claude/agents/稽核RD.md` |
| QA | 测试：功能／UI／逻辑／整合／回归 | `.claude/agents/QA.md` |

**不设 SA 角色，不加其他角色。**

## 3. 工作流与闸门

```
PM → RD1 + RD2 → 稽核RD → (FAIL → RD 修 → 重审，循环) → PASS → QA → (FAIL → RD 修 → 重测) → PASS → DONE
```

| 闸门 | 硬性规则 |
| --- | --- |
| 稽核RD | 发现**任何实质问题＝FAIL**，退回 RD；修完**必重审** |
| **稽核复审上限** | **最多复审 1 轮**。第 2 轮仍未通过 → **停下来问 OWNER**，不再自行循环 |
| QA 启动 | 稽核RD **明确 PASS** 才可开始 |
| 完成判定 | **QA 明确 PASS** 才算完成 |

闸门由 Team Lead 强制执行，OWNER 不需盯。

**为什么设复审上限**：同一件事修两轮还不过，通常代表**规格本身有问题**，不是 RD 不会修。继续循环只会烧 token，该回头找 OWNER 厘清需求。

## 3.1 闸门必须实际执行，不准只读码

| 角色 | 硬性要求 |
| --- | --- |
| 稽核RD | 必须真的开档读码到**档案:行号**；必须跑 `node local-server/check-contract.js` |
| QA | 必须**实际跑起来**：起 `local-server/`、跑 `check-contract.js`、能自动化的走 wechatide 指令 |
| QA 诚实回报 | 跑不动 / 只能人工测的部分，**明确标示「需要 OWNER 手动测」**，不准当成测过了 |

**为什么**：本专案的 bug（跳转错乱、键盘挡按钮、选项选不动）**静态读码抓不到**，过去都是 OWNER 在微信开发者工具实测才撞到。只读码就 PASS 的闸门等于没挡。

## 3.2 平行开发的边界由 Team Lead 明确切分

RD1 与 RD2 **看不到对方**，无法真正互相协调。因此：

| 规则 | 说明 |
| --- | --- |
| 边界指派 | Team Lead 分派时**明确指定每个 RD 只能碰哪些档案／模组**，不靠 RD 自觉 |
| 共享档案 | `services/`、`repositories/`、`utils/`、`components/`、`cloudfunctions/businessData/` 属高风险共享区，**同一轮不得由两个 RD 同时修改同一档** |
| 单 RD 优先 | 任务规模不大时**只派 RD1**，协调成本高于平行效益时不强行双开 |

## 3.3 PM 修改可信源需 OWNER 过目

`DOC/BUSINESS_LOGIC_PRINCIPLES.md` 等文件是唯一可信源，**没有人稽核 PM**。
PM 写错规格会污染可信源，后面所有人照着错的做。

| 规则 | 说明 |
| --- | --- |
| 先给 diff | PM 要改 `DOC/` 任何档案前，**先把 diff 呈给 OWNER**，点头才写入 |
| 盘点阶段 | 唯读盘点不改档，不受此限 |

## 4. 任务类型与是否需要 plan

| 任务类型 | 需要先给计画吗 |
| --- | --- |
| 唯读盘点／稽核／调查 | 否，不改档案无计画可审 |
| 实作／修改／重构 | 是，Team Lead 先给排序建议，OWNER 拍板才动手 |

## 5. 成本控制（Token 与 OWNER 控管成本）

### 5.1 派工时的成本纪律（Team Lead 执行）

| 规则 | 说明 |
| --- | --- |
| **只给 diff，不给整包** | Agent 冷启动重读六份 `DOC/` + 全站 grep 是最大 token 黑洞。审查类任务只喂改动范围 |
| **盘点只跑一次** | 结果落进 `进度总览.md`，后续 agent 读摘要，不重扫全专案 |
| **单 RD 优先** | 规模不大时只派 RD1。两个 RD 若会碰同一批档案，平行反而增加协调与冲突成本 |
| **稽核优先用 `/code-review`** | 内建指令只看 diff，比 spawn 稽核RD 便宜。**仅在改动跨模组、涉权限金流、或 `/code-review` 判不出规格符合度时**才派稽核RD |
| **不重复派工** | 同一件事已有 agent 报告，直接用，不为「再确认一次」重跑 |

### 5.2 稽核路径怎么选

| 改动性质 | 用什么稽核 |
| --- | --- |
| 单一模组、纯实作、无权限金流 | `/code-review` |
| 跨模组／改权限、鉴权、金流／地端云端镜像 | 派 **稽核RD**（需比对规格，非纯 code review） |
| RD1 + RD2 平行产出 | 派 **稽核RD**（要查整合冲突） |

### 5.3 减少 OWNER 拍板次数

OWNER 的控管成本主要来自「待拍板项太多」，不是 agent 数量。

| 类型 | 谁决定 |
| --- | --- |
| **纯技术取舍**（答案唯一或有明确最佳解） | **Team Lead 直接定**，一行说明结论即可，不问 OWNER |
| **一致性清理**（去重／删冗余／留哪个） | Team Lead 直接定 |
| **安全边界**（例如「软删团单能不能下单」→ 一律挡） | Team Lead 直接定，从严 |
| **产品方向**（两种做法都成立、影响使用者体验或画面结构） | **OWNER 拍板** |
| **推翻既有已拍板决策** | OWNER 拍板 |

**待拍板项到期机制**：`PAGE_MAP.md` §4、`FIELD_DICT.md` §9 的 ❓ 项目，
**挂超过一轮开发未获拍板者，由 Team Lead 依上表判定**；属产品方向的才继续保留待 OWNER。

## 6. 自动化闸门（不靠人盯）

| 闸门 | 现况 | 位置 |
| --- | --- | --- |
| 契约检查 | ✅ 已挂 pre-commit，7 项，约 1 秒 | `.husky/pre-commit` → `local-server/check-contract.js` |
| lint | ✅ 已挂 pre-commit | `.husky/pre-commit` → `lint-staged` |
| 冒烟测试 | 手动 `npm run smoke` | `local-server/automator-smoke.js` |

**原则**：能被脚本挡下的错误，就不该消耗 agent 或 OWNER 的注意力。
新增同类检查一律优先挂进 `check-contract.js`，而不是写成「请记得检查」的文件条目。

## 7. 文件规则（全体适用）

| 规则 | 说明 |
| --- | --- |
| 预设不新建文件 | 依主题归位既有 `DOC/` 档案 |
| 禁止流水帐 | 不写「我先做了什么、再改了什么」，git log 已有 |
| 过程产物不进 DOC | 稽核报告、测试纪录属过程产物 |
| 任务结束清理 | 暂时性文件用完删除 |
