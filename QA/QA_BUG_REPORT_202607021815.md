# QA BUG Report - 2026-07-02

## 測試範圍
- 專案：導遊領隊早下班微信小程序
- 測試目標：不只測功能是否能跑，也檢查功能是否完整、是否能讓真人使用、是否能應付現實業務情境。
- 主要驗收來源：`CURRENT_TASKS.md`、`PROJECT_RULES.md`、`MVP_COMPLETION_CHECKLIST.md`、`ACCEPTANCE.md`、`HANDOFF.md`、`DATA_MODEL_AND_PERMISSIONS.md`、`QA/QA_SEED_REQUIREMENTS.md`
- 測試日期：2026-07-02

## 已執行檢查
- `npm run lint`：通過
- `git diff --check`：通過
- `app.json` 27 個 route 的 `.js/.ts`、`.wxml`、`.json` 靜態存在檢查：通過

## 測試結論
目前程式碼已有導遊團單、商品庫、客戶訂單、收款狀態、微信雲端 repository 的基礎，但不能宣告「真人可用 MVP」。最大缺口不是單一 crash，而是現實使用閉環不足：客戶如何進入團單、商品圖片如何跨設備保存、開團資料是否足夠、付款如何被可靠追蹤，以及 UI 是否清楚區分正式雲端與 QA/local 狀態。

## BUG-001 P0 客戶真實下單入口不完整：團單沒有可用分享/小程序碼/二維碼閉環

### 影響
真人客戶目前很難從現實場景進入指定團單下單。導遊能在內部頁點「客户下单」，但這不是導遊發給客戶的可用入口。若沒有可分享的小程序路徑、微信分享卡片或小程序碼，核心 MVP 的「導遊開團 -> 客戶下單」閉環不成立。

### 證據
- `sub-pages/groupOrder/add/index.wxml:5-36`：開團表單只有名稱、描述、商品設定，沒有分享設定、收單截止、客戶入口產生。
- `cloudfunctions/businessData/index.js:225-237`：`qrCodeUrl`、`sharePath` 預設為空字串，建立團單時沒有產生可分享入口。
- `sub-pages/groupOrder/detail/index.ts:129-158`：預覽 QR 時如果沒有 `qrCodeUrl` 只顯示「暂无团单二维码」。
- `sub-pages/groupOrder/detail/index.ts:275-293`：客戶下單入口是內部 `navigateTo('/pages/customerOrders/edit/index?groupOrderId=...')`，不是可交給外部客戶使用的分享方案。

### 預期
- 團單建立成功後，至少要有一個真人可用入口：
  - 微信分享卡片，帶 `groupOrderId`。
  - 或小程序碼/二維碼，可被客戶掃碼進入下單頁。
  - 或明確的「複製/分享下單入口」。
- 客戶從分享入口進來時，要能完成登入/角色識別並回到該團單下單頁。

### 複測
1. 導遊建立團單。
2. 從團單詳情產生或分享客戶入口。
3. 用客戶身份從入口進入。
4. 客戶選商品、填資料、提交訂單。
5. 導遊端能看到該訂單。

## BUG-002 P0 商品圖片只保存臨時路徑，跨會話/跨用戶會失效

### 影響
商品圖片是客戶判斷商品的重要資訊。現在新增商品時只保存 `tempFilePath`，若保存到雲端後沒有上傳到雲存儲，其他用戶或重新打開小程序時圖片可能失效。

### 證據
- `sub-pages/product/add/index.ts:110-119`：`wx.chooseMedia` 後直接把 `res.tempFiles[].tempFilePath` 放進 `currentProduct.pictureUrls`。
- `sub-pages/product/add/index.ts:128-164`：保存商品時直接 `ProductService.create(p)`，沒有 `wx.cloud.uploadFile` 或其他 durable upload。
- `cloudfunctions/businessData/index.js:163-178`：雲端保存 `pictureUrls` 原值，沒有轉換成 cloud file ID 或正式 CDN URL。

### 預期
- 正式雲端模式下，圖片保存前必須上傳到微信雲存儲或正式圖片服務。
- `pictureUrls` 應保存 durable `cloud://` fileID 或 HTTPS URL。
- 若圖片上傳尚未完成，UI 必須明確提示「圖片暫不支持正式保存」，不可讓使用者以為已完成。

### 複測
1. 導遊新增商品並上傳圖片。
2. 保存後退出/重開小程序。
3. 用同一導遊、另一個客戶身份查看商品與下單頁。
4. 圖片仍可顯示。

## BUG-003 P1 開團資料不足以應付真實團購/帶團情境

### 影響
現實團單通常需要出團日期、集合/取貨方式、收單截止、付款說明、導遊聯絡方式、客戶備註提示等資訊。現在開團只填名稱、描述、商品，會導致客戶不知道何時截止、去哪取貨、怎麼付款，導遊也無法管理不同日期/場次。

### 證據
- `sub-pages/groupOrder/add/index.wxml:5-36`：表單只包含名稱、描述、商品。
- `DATA_MODEL_AND_PERMISSIONS.md` 已定義 `startAt`、`endAt`、`sharePath` 等正式欄位，但頁面沒有輸入或展示。
- `pages/customerOrders/edit/index.wxml:6-10`：客戶下單頁只顯示團單標題、描述、狀態，缺少截止、付款、取貨/交付資訊。

### 預期
MVP 至少要補上：
- 團單日期/場次或出團時間。
- 收單截止或停止收單說明。
- 取貨/交付/集合說明。
- 付款方式或付款備註。
- 導遊/領隊聯絡資訊或客服說明。

### 複測
用一個真實旅遊團購案例建立團單，客戶只看小程序內容也能知道買什麼、何時截止、怎麼付款、如何取貨/領取。

## BUG-004 P1 UI 仍大量顯示本地/QA/Phase 8 舊文案，會誤導真人使用者

### 影響
專案文件顯示正式微信雲登入與核心業務雲端保存已接通，但多個頁面仍硬寫「本地/QA」「尚未正式保存」「Phase 8 後接入」。真人使用時會不知道自己的資料到底有沒有正式保存。

### 證據
- `pages/home/index.wxml:17-19`：顯示「正式云端保存与真 OpenID 仍在 Phase 8 gate」。
- `pages/release/index.wxml:6`：新建團單描述仍寫「保存到本地/QA repository」。
- `pages/setting/index.js:20-30`：資料模式固定寫「本地/QA 展示模式」與「Phase 8 后接入」。
- `pages/productManagement/index.wxml:17-20`：空狀態固定寫「本地/QA 模式尚未正式保存」。

### 預期
- 文案要依 `meta.saveMode`、`session.isMockOpenId`、`cloudOpenIdVerified` 動態顯示。
- 正式雲端成功時顯示「已保存到微信雲端」。
- mock/local fallback 時才顯示 QA/local 警示。
- 不要在正式使用入口顯示過期 Phase 文案。

### 複測
1. 正式微信 OpenID 登入後查看首頁、設定、商品庫、開團入口。
2. 所有資料模式文案與實際 session/save mode 一致。
3. 切到 mock/local fallback 時才出現 QA/local 警示。

## BUG-005 P1 登入角色選項與雲端實際角色規則不一致

### 影響
登入頁讓使用者選「產品擁有者 / 運營管理員」，但 `authLogin` 雲函數對非白名單 OpenID 只允許 guide/customer。使用者選 admin/owner 後實際可能被降成 guide，卻只看到「登录成功」，容易誤判權限或以為管理後台壞掉。

### 證據
- `services/auth/roleScope.js:17-22`：登入選項包含 guide、customer、owner、admin。
- `pages/login/login.wxml:7-16`：直接讓使用者選所有 `roleOptions`。
- `cloudfunctions/authLogin/index.js:21-29`：只有白名單 OpenID 才是 owner/admin，否則非 customer 會 normalize 成 guide。
- `pages/login/login.js:24-41`：登入成功後沒有提示「你選的 admin/owner 未生效，已按白名單規則登入為 guide」。

### 預期
- 未配置白名單時，正式登入頁只提供 guide/customer，或將 owner/admin 標為需白名單並禁用。
- 若使用者選了 owner/admin 但雲端返回 guide/customer，必須顯示明確提示。
- 設定頁/我的頁要顯示實際角色來源與限制。

### 複測
1. 非白名單 OpenID 選 owner/admin 登入。
2. UI 明確告知無白名單權限，實際登入角色為 guide/customer。
3. 不允許使用者誤以為自己已有管理權限。

## BUG-006 P1 付款流程缺少現實核對資料，無法可靠處理真實收款

### 影響
目前客戶只能「聲明已付款」，導遊只能「確認收款」。沒有付款方式、付款截圖、交易流水、實收金額、確認備註。現實上會遇到少付、多付、代付、重複聲明、導遊誤點確認、退款/撤回等情況，現在很難追蹤與糾錯。

### 證據
- `pages/customerOrders/index.js:87-125`：訂單動作只有聲明付款、確認收款、取消訂單。
- `cloudfunctions/businessData/index.js:467-523`：狀態更新只寫狀態與簡單 note；確認付款時建立 payment，但沒有客戶付款方式、付款憑證、實收金額輸入。
- `pages/customerOrders/edit/index.wxml:16-53`：客戶下單頁沒有付款方式或付款說明。

### 預期
至少補上 MVP 級別的人工收款欄位：
- 客戶付款方式/付款備註。
- 可選付款截圖或憑證。
- 導遊確認時可填實收金額與備註。
- 狀態歷史可看到誰在何時做了什麼、備註是什麼。

### 複測
建立一筆訂單，客戶填付款備註/憑證後聲明已付，導遊確認時填實收資訊，訂單詳情與歷史能完整查看。

## BUG-007 P2 客戶姓名與手機欄位驗證不足

### 影響
客戶可以輸入任意手機內容，只要非空就能提交。現實交付時若手機格式錯誤，導遊無法聯絡客戶。

### 證據
- `pages/customerOrders/edit/index.wxml:16-19`：手機欄位是普通 `t-input`，沒有 phone 類型或格式提示。
- `services/customerOrder/customerOrderService.js:130-133`：只檢查 `customerPhone` 是否非空，沒有格式或長度驗證。

### 預期
- 中國大陸手機號至少做 11 位與基本號段格式驗證，或若要兼容境外號碼，需明確標示格式並允許國碼。
- 錯誤時阻止提交並提示具體原因。

### 複測
輸入空字串、字母、過短號碼、合法手機號，只有合法格式能提交。
